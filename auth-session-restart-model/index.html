    LoBAC Auth Restart and JWT Key Model¶

    LoBAC v0 uses a restart-invalidates-all auth/session model.

    Restart Semantics¶

    Daemon restart invalidates every in-memory HTTP session, access token, refresh token, refresh successor, refresh reuse marker, and logout tombstone. Clients must treat any authentication failure after restart as a full reauthentication requirement.

    Stable wire errors after restart:

    • Bearer-protected endpoints return their existing *_auth_required code.
    • /auth/refresh returns refresh_auth_required.
    • Tenant mismatch remains fail-closed through tenant_invalid or tenant_denied before endpoint-specific authorization continues.

    This model intentionally does not persist refresh-token state. A restart cannot resurrect a logged-out session or revoked refresh token because no previous token state is reloaded.

    Policy Commit Durability¶

    Human accounts, grants, permission states, and MFA enrollment are policy data, not restart-valid session credentials. A successful standalone outer policy commit publishes the encrypted policy image durably before acknowledging the operation, so fresh MFA login still works after abrupt process termination. Disabled or deleted accounts remain unavailable. Old credentials still expire on restart as described above.

    Nested savepoint commits defer publication until their outer transaction commits. Coordinator-fenced operations defer it until the coordinator's explicit publication step; releasing the fence does not publish. Failed or ambiguous encrypted publication makes the store terminal and prevents close from republishing its in-memory state. Reopen the store and recover through the existing recovery path rather than continuing to use that connection.

    Encrypted policy stores use an in-memory SQLite image. Each standalone outer commit serializes and encrypts the complete image, with O(policy-image-size) work and synchronous durable canonical-file replacement. The authority and SQLite connection mutexes remain held through publication, blocking other same-connection operations, including read snapshots, during that interval. On Windows, transient canonical-file replacement errors may add at most 500 ms of backoff (ten 50 ms waits), plus I/O and scheduler time, while both mutexes remain held. Retries reuse the same flushed encrypted image; they never replay SQL commits. Persistent contention fails closed and makes the store terminal without close-time republication. Plaintext SQLite commits retain their existing durability behavior.

    The temporary file is held open by handle, with no sharing, from creation until it is renamed or removed, and the rename goes through that handle (SetFileInformationByHandle with FileRenameInfo). Another process therefore cannot rename, delete or substitute the temporary file while a publication is in progress. Before each attempt the store re-checks the held file's identity and link count, because a hard link can still be added through an attribute-level open. A failed or refused publication removes only that held file, through its handle, and never deletes by path. The one exception is that, before creating its temporary file, the store reclaims a leftover file from an interrupted earlier run at the reserved temporary name, as the POSIX writer does before it creates its temporary file.

    The canonical name cannot be held the same way, so the check for a reparse point there is path-based and leaves a residual window before each rename. A reparse point planted at the final component in that window is not followed: a file symbolic link is replaced as a link, a junction or other reparse point is refused on the next attempt, and a plain directory makes every attempt fail until the publication fails closed. Ancestor directories are outside this check and must remain operator-protected for the store's lifetime.

    Session Credentials and Internal Identity¶

    Human login returns an opaque session_token: wst_ followed by 64 lowercase hexadecimal characters encoding 32 random bytes. It is independent of the internal UUID session ID. The daemon retains only a SHA-256 digest for credential lookup; JWT claims, session state, policy scopes, and revocation markers use the internal ID. Neither that ID nor the digest authenticates as a session token. Service sessions do not have a human session credential.

    MFA verification returns the same session token. Refresh responses, including idempotent replays, omit session_token: they rotate access/refresh tokens and do not recover or replace the original secret. Clients must retain the secret from login if they need session-token authentication. The C client preserves it on ordinary refresh; replacing its refresh token explicitly clears the old session secret, so restoring only a refresh token yields bearer-only state. External clients that required session_token in refresh responses must adapt. Login and MFA responses still include it.

    The legacy /decide parameter named session_token also accepts policy scopes. A live wst_ credential is translated to its internal ID before evaluation; an unresolved value with that reserved prefix is rejected, including a logged-out token. Other policy scope values retain their existing meaning.

    New session-related audit fields store session# followed by 64 lowercase hex characters: SHA-256 of wyrelog.audit.session.v1: followed by the internal ID. This deterministic correlation handle is not a credential or a policy scope. Session-state and session-event subjects always use it; decision resources and permission/membership scopes use it only for known session identities. Other resources, including unrelated UUIDs, retain their original representation.

    A handle-local digest set classifies identities before session publication and retains them through logout for delayed removal events. This set grants no access and does not track liveness. Startup rebuilds it from persisted session lifecycle events before loading policy facts; it does not classify ordinary tenant scopes. HTTP service sessions register their identity before publication.

    Existing hash-chained audit rows are not rewritten. Legacy read-time structural and live-ID redaction remains in place, using process-local keyed handles with 16 hex digits. Newly stored 64-digit handles pass through unchanged. A restart invalidates old credentials, including those that once doubled as internal IDs; historical files still require their existing protections.

    JWT Signing Key Custody¶

    Production JWT signing key material is rooted in the configured production KeyProvider spec. Packaged Linux services use systemd-creds:NAME, where systemd exposes the credential under $CREDENTIALS_DIRECTORY; manual operator checks may use file:PATH. On each daemon boot, the daemon derives a JWT root secret from the KeyProvider and mixes in a random boot epoch before issuing tokens. The boot epoch is reflected in the JWT kid, so tokens from a previous process epoch fail the key-id gate before they can bind to live token state.

    Non-production mode continues to use process-local random JWT key material.

    Rotation Behavior¶

    JWT signing-key rotation is epoch rotation. Rotating the epoch clears active access-token and refresh-token state and changes the JWT kid. Existing session handles remain in memory, but clients must login again because old access and refresh tokens no longer authenticate.

    Operator runbook:

    1. Rotate the production KeyProvider material if the root must change.
    2. Restart the daemon to create a new boot epoch.
    3. Expect all clients to receive *_auth_required or refresh_auth_required and perform a fresh login.
    4. Confirm /readyz returns ready before admitting traffic.
